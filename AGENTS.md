Always open and consult **[ARCHITECTURE.md](ARCHITECTURE.md)** to understand system specifications and data flows before modifying code. Do not duplicate architectural descriptions here.

---

## 1. System Scope & Core Invariants

- **Zero-Knowledge Architecture:** Synclo is strictly zero-knowledge. The server is solely an encrypted relay and blind storage mediator. Plaintext passwords, Master Keys, derived keys, or decrypted clipboard payloads must never touch the server, be accepted by APIs, or be logged. Payloads remain opaque blobs. (For technical cryptographic specifications, see [ARCHITECTURE.md](ARCHITECTURE.md)).
- **Single-Node Deployment Only (VPS / Homelab):** This backend is designed exclusively as a single-node server for self-hosters running on a personal VPS or homelab (via Docker Compose or bare metal with SQLite and local Redis). There are **no plans for multi-node clustering or distributed deployment**. Do not add distributed systems complexity, multi-node consensus, cluster topologies, or unnecessary horizontal scaling overhead.
- **Code Simplicity & Human Comprehension:** Never overcomplicate code. The simpler the code, the better. Simple does not mean writing fewer lines or compressing logic into dense one-liners; it means that if a human developer reads through the codebase, they should not have to spend hours trying to understand it. Write direct, explicit, and readable logic over clever abstractions. Every modification must pass the test: *Would a human engineer understand this immediately without friction?*
- **SQLite Concurrency Rule:** Never call bare `db.commit()`. All database mutations must use `run_in_write_transaction` or `async_run_in_write_transaction` from [app/database/engine.py](app/database/engine.py) to prevent SQLite lock escalation deadlocks.
- **Database Migrations:** Any change to models in [app/database/models.py](app/database/models.py) requires an autogenerated Alembic migration (`alembic revision --autogenerate -m "..."`).

## 2. Code Philosophy: Simplicity & Clarity

- **Clarity Over Cleverness:** Explicit code is superior to compact or clever constructs. Avoid dense chained operations, nested ternaries, and complex metaprogramming. If a compact expression requires a mental pause to parse, write it explicitly.
- **Solve the Immediate Problem:** Implement exactly what is needed for the task or bug fix. Avoid speculative generalization, premature optimization, wrapper bloat, and unneeded abstractions (do not build factories or interfaces until multiple concrete use cases exist).
- **Preserve Exact Behavior:** When simplifying or refactoring, preserve all inputs, outputs, ordering, side effects, and error semantics. Refactoring must never change observable behavior or weaken error handling.
- **High-Signal Code & Comments:** Code should be self-documenting. Write comments only to convey intent or rationale ("why", not "what"). Delete trivial comments that merely restate what the code visibly does.

## 3. Code Review & Quality Standards

Before presenting any code modification, evaluate the change across these five review axes:

1. **Correctness:** Does the code satisfy the task requirements? Are edge cases, boundary conditions, and error paths handled? Do all existing tests pass?
2. **Readability & Comprehension:** Can another engineer understand the flow without assistance? Is control flow straightforward? Are functions focused and well-named?
3. **Architecture:** Does the change respect the single-node architecture and existing module boundaries? Avoid leaking feature-specific logic into general-purpose utilities. Prefer removing dead code or unnecessary wrappers over polishing them.
4. **Security:** Does the implementation preserve the Zero-Knowledge boundary? Are inputs validated, SQL parameterized via SQLAlchemy, and sensitive credentials/tokens kept out of logs and exceptions?
5. **Performance:** Are there unconstrained queries, N+1 query patterns, missing pagination, or synchronous blocking calls in async event paths?

### Change Sizing & Structural Cleanliness
- **Keep Changes Focused:** Keep modifications small, self-contained, and easily reviewable.
- **Separate Refactoring from Feature Work:** Never combine broad refactoring with new feature additions or bug fixes in a single change.
- **Concrete Remedies:** When simplifying complex structures, propose explicit improvements (guard clauses, early returns, or extracting focused helpers) rather than shuffling complexity across files.

## 4. Git Invariant: No Automatic Commits Ever

- **NEVER Commit Automatically:** AI agents must **never** run `git commit`, `git push`, create git tags, or alter git history automatically unless the user explicitly and directly instructs you to do so.
- Staging, committing, reviewing diffs, and branch workflows belong strictly to the user.

---

## 5. User Interaction & Workflow Guidelines

- **Concise & Direct Communication:** Keep responses focused on what was done, why it was done, and what was verified. Avoid conversational filler or regurgitating file contents.
- **Clickable File Links:** Always provide clickable GitHub-style markdown links for touched files (e.g. `[filename](path/to/file)`).
- **Clarify When Unsure:** If requirements are ambiguous or a decision affects existing client behaviors, ask the user for clarification rather than making assumptions.
- **Verification First:** Never declare a task complete without running the verification suite to prove zero regressions.
- **Documentation Updates & README Invariant:** Whenever a new feature or fix is added that requires documentation, add the proper technical documentation directly to [ARCHITECTURE.md](ARCHITECTURE.md). If [README.md](README.md) needs any changes, **always ask the user first** before modifying `README.md`.
